# MealMate Backend

Express + PostgreSQL REST API for MealMate — campus meal planning and
actual-expense tracking. Implements the functional requirements from the
v2.0 requirements report: authentication/profile, guest-first catalog
browsing, favorites, daily budget, meal-plan persistence (automatic and
manual), independent actual expenses, read-only meal history and reports,
and conflict-aware guest-to-account transfer.

## Folder structure

```
backend/
├── config/       # Environment, PostgreSQL pool, schema, first-run seed
│   ├── db.js         # pg Pool, query helper, transactions
│   ├── schema.sql    # Idempotent CREATE TABLE statements
│   ├── migrate.js    # Runs schema.sql on startup
│   ├── env.js        # DATABASE_URL + app settings
│   └── seed.js       # Sample catalog + admin account
├── controllers/  # Business logic for routes
├── middleware/   # Auth (JWT), validation, rate limiting, error handling
├── models/       # SQL data-access modules (User, Food, Favorite, DailyBudget, MealPlan, Expense)
├── routes/       # Express API route endpoints
├── utils/        # Shared domain constants + date-only helpers (Asia/Yangon aware)
├── .env          # Environment variables (PORT, DATABASE_URL, JWT_SECRET, ...)
└── server.js     # Entry point (Express app initialization)
```

## Setup

Requirements: Node.js >= 18 and a running PostgreSQL server (13+; developed
against PostgreSQL 18).

```bash
# 1. Create the database (tables are created automatically on startup)
psql -U postgres -c "CREATE DATABASE mealmate;"

# 2. Configure the connection string in backend/.env
#    DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@127.0.0.1:5432/mealmate

# 3. Install and run
cd backend
npm install
npm run dev        # nodemon, http://localhost:4000/api
# or
npm start
```

On startup the API connects to PostgreSQL, runs the idempotent schema
(`config/schema.sql`), and seeds the sample campus catalog plus an admin
account (`admin@mealmate.local` / `Admin#1234` by default — change these).
Seeding is controlled by `SEED_CATALOG` / `SEED_ADMIN` in `.env`.

> `.env` notes: quote values containing `#` (e.g. `ADMIN_PASSWORD="Admin#1234"`),
> otherwise dotenv treats the rest of the line as a comment. If your database
> password contains URL-reserved characters (`@`, `:`, `/`, `#`, ...), percent-
> encode them in `DATABASE_URL`.

### PostgreSQL notes

- All primary keys are UUID v4 values generated by Node (`crypto.randomUUID()`),
  so no database extension is required.
- Money is stored as whole-MMK `integer` columns; calendar days as `date`.
- Plan and expense saves run inside a transaction, so a failed save never
  leaves a partial day. Deleting a plan cascades its snapshot items but keeps
  the day's budget.
- Set `PGSSL=true` for managed providers that require TLS.

## Response envelope

Success:

```json
{ "success": true, "data": { ... } }
```

Error (field-level `details` map straight to the Flutter form errors):

```json
{ "success": false, "message": "...", "details": [{ "field": "amount", "message": "..." }] }
```

All money values are whole numbers in MMK (kyat). All dates are `YYYY-MM-DD`
strings; "today" is resolved in `APP_TIMEZONE` (default `Asia/Yangon`).

## Endpoints

### Health

| Method | Path | Notes |
| ------ | ---- | ----- |
| GET | `/api/health` | Liveness + database connection state |

### Auth & profile (FR-01..FR-06)

| Method | Path | Body / Query | Notes |
| ------ | ---- | ------------ | ----- |
| POST | `/api/auth/register` | `{ name, email, password }` | 201 `{ token, user }`; bcrypt hashing |
| POST | `/api/auth/login` | `{ email, password }` | 200 `{ token, user }`; updates `lastLoginAt` |
| GET | `/api/auth/me` | — | Current user (Bearer token) |
| POST | `/api/auth/logout` | — | Stateless JWT — client discards the token |
| PATCH | `/api/users/me` | `{ name }` | Update profile |
| PATCH | `/api/users/me/password` | `{ currentPassword, newPassword }` | Verifies current password |

User JSON: `{ id, name, email, role, isActive, lastLoginAt, createdAt, updatedAt }`.

### Foods catalog (FR-07..FR-11) — browse is public (guest-first)

| Method | Path | Body / Query | Notes |
| ------ | ---- | ------------ | ----- |
| GET | `/api/foods` | `?category=Rice Dishes&search=mohinga&sort=name|price|-price|newest&page=&limit=` | Search spans food **and** shop names across all categories |
| GET | `/api/foods/:id` | — | Single entry |
| POST | `/api/foods` | `{ name, shopName, location?, category, price, imagePath? }` | Admin only |
| PATCH | `/api/foods/:id` | partial fields | Admin only |
| DELETE | `/api/foods/:id` | — | Admin only; soft delete + favorites cleanup |

Categories: `Rice Dishes, Noodles, Soups, Salads, Others`.

### Favorites (FR-12) — authenticated only

| Method | Path | Body / Query | Notes |
| ------ | ---- | ------------ | ----- |
| GET | `/api/favorites` | — | With food details |
| POST | `/api/favorites` | `{ foodId }` | 409 when already favorited |
| DELETE | `/api/favorites/:foodId` | — | |

### Daily budget (FR-13..FR-16)

| Method | Path | Body / Query | Notes |
| ------ | ---- | ------------ | ----- |
| GET | `/api/budget` | `?date=YYYY-MM-DD` (default today) | 404 when none set |
| PUT | `/api/budget` | `{ date?, amount }` | Upsert for that day. Editing a budget never creates expenses and never modifies/deletes a saved plan (over-budget state returned as a warning) |

### Meal plans (FR-17..FR-26, FR-39..FR-44)

| Method | Path | Body / Query | Notes |
| ------ | ---- | ------------ | ----- |
| GET | `/api/plans` | `?date=` (default today) | Saved plan + budget + remaining |
| POST | `/api/plans` | `{ date?, method: auto\|manual, items: [{ foodId, quantity, mealType }] }` | See rules below |
| DELETE | `/api/plans` | `?date=` | Deletes **only** the plan; the day's budget is kept |

Server-side rules:

- A budget for the date must exist first (planning gate).
- Prices are snapshotted from the catalog at save time (immutable).
- `auto` plans must fit the budget — over-budget automatic plans are
  rejected with 422 (never saved).
- `manual` plans may exceed the budget; the response flags `overBudget`
  (warning, save still permitted).
- One plan per user per day — saving again replaces it
  (last-saved-plan-wins).
- Saving a plan never creates expense records (planning is not spending).

### Actual expenses (FR-27..FR-34) — authenticated only

| Method | Path | Body / Query | Notes |
| ------ | ---- | ------------ | ----- |
| GET | `/api/expenses` | `?date=` (default today) | Day record + totals per meal type |
| POST | `/api/expenses` | `{ date?, items: [{ name, quantity, unitPrice, mealType }] }` | Atomically replaces the whole day |
| DELETE | `/api/expenses` | `?date=` | |

Rules: date defaults to today; past dates allowed; **future dates
rejected**. Names and prices are manually entered — no catalog selection,
no plan prefill, no price inheritance. Each meal type can hold multiple
items. All items for a date are written in one transaction (no partial
days).

### Meal history (FR-35..FR-36) — read-only

| Method | Path | Query | Notes |
| ------ | ---- | ----- | ----- |
| GET | `/api/history` | `?from=&to=&page=&limit=` (default last 30 days) | Days with totals; derived only from saved expenses; use `/api/expenses?date=` for corrections |

### Reports (FR-37..FR-38) — read-only

| Method | Path | Query | Notes |
| ------ | ---- | ----- | ----- |
| GET | `/api/reports` | `?period=daily\|weekly\|monthly&from=&to=` | Totals + meal-type breakdowns computed solely from actual expenses |

### Guest-to-account transfer (FR-04/FR-05, AT-10)

| Method | Path | Body | Notes |
| ------ | ---- | ---- | ----- |
| POST | `/api/guest-transfer` | `{ date?, budget?: { amount }, plan?: { method, items }, resolution? }` | Push today's guest budget/plan after login/sign-up |

Collision handling: budget and plan are checked independently. When the
account already has data for the date, the API replies **409** with the
conflicting items in `details` — the client must ask the user and resubmit
with `resolution: 'keep-account'` or `'replace-with-guest'`. Nothing is ever
silently overwritten; non-conflicting items always transfer. The writes are
applied in a single transaction.

## Example session

```bash
# Register
curl -X POST http://localhost:4000/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name":"Aung Aung","email":"aung@student.edu","password":"password123"}'

# Export the token
TOKEN=...   # from the register/login response

# Set today's budget
curl -X PUT http://localhost:4000/api/budget \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"amount": 10000}'

# Save a manual plan (foodId from GET /api/foods)
curl -X POST http://localhost:4000/api/plans \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"method":"manual","items":[{"foodId":"<uuid>","quantity":1,"mealType":"breakfast"}]}'

# Record actual spending for today (independent of the plan)
curl -X POST http://localhost:4000/api/expenses \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"items":[{"name":"Mohinga","quantity":1,"unitPrice":2000,"mealType":"breakfast"}]}'

# Read history and reports
curl "http://localhost:4000/api/history" -H "Authorization: Bearer $TOKEN"
curl "http://localhost:4000/api/reports?period=weekly" -H "Authorization: Bearer $TOKEN"
```

## Security notes

- Passwords: bcrypt (12 rounds); hashes are only fetched when explicitly
  needed and are never serialized.
- Sessions: stateless JWT (`JWT_EXPIRES_IN`, default 7d). Logout discards
  the token client-side; keep the lifetime short in production.
- Every authenticated query is scoped by `req.user.id` — cross-account
  access is not possible (AT-13).
- All SQL uses parameterized queries (`pg` placeholders), never string
  interpolation of user input.
- Rate limiting: 300 req/15 min per IP overall, 20 req/15 min on auth
  endpoints; helmet security headers; JSON body capped at 100 KB.
- Set a strong `JWT_SECRET`, a real `CORS_ORIGIN` list, and change the
  seeded admin password before deploying.
